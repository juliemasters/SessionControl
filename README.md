# SessionControl

Session-specific AlphaEdit weight deltas, activation routing, and a measured comparison with dense RAG and a reusable full-bank KV cache.

The latest completed experiment used nested banks of 24, 32, 48, and 64 LongMemEval sessions on physical GPU 1. Each memory write receives the **full answer-bearing session, original question, and supplied answer**. Recall asks that exact original question. The final answer is generated by the selected delta.

| Sessions | Our source routing | Our answer exact match | Matched RAG answer exact match | Full-bank KV answer exact match |
| --- | --- | --- | --- | --- |
| 24 | 24/24 | 24/24 | 24/24 | 6/24 |
| 32 | 32/32 | 31/32 | 32/32 | 15/32 |
| 48 | 48/48 | 45/48 | 47/48 | Unavailable: context limit |
| 64 | 64/64 | 58/64 | 63/64 | Unavailable: context limit |

Exact match normalizes case and punctuation across the complete delivered answer. These are lexical scores, not independent factual grading. The banks include previously inspected questions, and write and recall questions are identical: this is an exploratory mechanism and capacity experiment, not a held-out generalization result.

At 64 sessions the dense delta bank retains **42.0 GiB on disk**, versus **0.988 MiB of RAG text/index on CPU/disk**. Measured setup-and-recall peak live GPU allocation is approximately **31.04 GiB for deltas**, **31.31 GiB for RAG**, and **57.49 GiB for the largest runnable KV bank (32 sessions)**. Common float32 LLM weights account for approximately 29.92 GiB. Retained storage and live GPU allocation are different measures; these results do not establish a memory advantage over RAG.

## Connected write and recall experiment

1. **Write:** optimize independent deltas for FFN layers 13–15 using the full session as grounding, `Q: {original question}\nA:` as the key, and the supplied answer plus EOS as the target. Restore base weights after each write.
2. **Route:** capture base-model key activations for the bare original question. Score every stored delta using normalized delta activation energy, then choose the maximum with a fixed lexical session-ID tie rule.
3. **Generate:** activate only that selected delta, generate greedily, stop at EOS or a new conversation turn, and restore base weights.
4. **Evaluate:** compare selected source IDs and complete answers against the benchmark references, and record retained payload and measured GPU peaks separately.

The current router uses activations; it does not generate a candidate under every delta or use a BERT scorer. The 64×64 matrix contains **4,096 energy scores**, not 4,096 generated answer probes. The earlier BERT prototype remains available in [the archived README](docs/archive/LEGACY_BERT_ROUTING.md) and `section_b.py`.

## Reproduce

See [the clean-checkout instructions](docs/REPRODUCING.md) for the pinned dataset, local model setup, GPU 1 guard, projection construction, 64 independent writes, and baseline comparison. Model weights, delta tensors, projections, raw conversations, and caches are excluded from this repository.

The clean-checkout preparation and CPU checks were verified during packaging. The new bootstrap entry point has not yet been run end to end on a GPU. Published reports describe the completed historical experiment, not a new execution of that entry point.

For local CPU checks:

```bash
python -m pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cpu
python -m pip install -r requirements-experiments.txt
CUDA_VISIBLE_DEVICES="" python -m unittest discover -v
CUDA_VISIBLE_DEVICES="" python -m unittest discover -s tests -v
python scripts/verify_release.py
```

## Files

| Location | Purpose |
| --- | --- |
| `scripts/prepare_experiment.py` | Reconstruct the exact 64-session cohort and preservation corpus from the pinned dataset |
| `scripts/bootstrap_experiment.py` | Write a fresh 40-delta source bank, then run the remaining 24 writes and all nested comparisons |
| `experiment_memory_scaling.py` | Activation routing, generation, RAG/KV baselines, measurement, and completion checks |
| `answer_only_generation.py` | EOS/next-turn stopping and bounded reference containment |
| `memory_comparison_core.py` | Dense retrieval and reusable, cropped KV-cache operations |
| `docs/results/` | Completed reports, PNG/SVG graphs, outputs, measurements, and export hashes |
| `config/session_manifest.json` | Original question/session identifiers, cohort order, and prior-use labels |

Historical experiment entry points retain dependencies on their earlier run directories. Use the bootstrap entry point for a fresh checkout. Exported reports contain public benchmark question/answer excerpts; complete dataset conversations are reconstructed locally.
